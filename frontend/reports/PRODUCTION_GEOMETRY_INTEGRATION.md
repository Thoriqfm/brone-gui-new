# Production Geometry Integration — Phase 1

Date: 2026-11-02, updated after the browser feedback about excessive fades. The production face architecture accepts an opt-in procedural renderer for all seven canonical expressions. All 42 distinct directed canonical transitions now morph eyes and mouth independently using existing validated legs, with explicit Idle bridges where necessary. The original asset renderer remains the default. Browser/target-display approval is outstanding; this report does not declare full visual parity or authorize a default change.

## 1. Existing production rendering architecture

`requestExpression` validates semantic requests and updates the existing Zustand `faceStore`. WebSocket input continues through its existing runtime parser/controller. `FaceRenderer` reads `emotion` and `transitionMs`; `useExpressionTransition` owns a mount-scoped coordinator connected to the existing `animationEngine` and Anime.js driver.

Previously, the coordinator rendered approved SVG images through `Eyes`, `Mouth`, `FaceBase` and `FaceEffects`. Idle → Happy used its existing element preset; other non-immediate transitions crossfaded two compositions. The procedural engines were exposed by development previews. The inspected implementation, rather than the older scaffold descriptions in the short architecture/animation documents, establishes this current behavior.

The integration preserves the asset branch, including its element preset and preview-only `happier-transition`. There are no changes to the backend, shared schema, runtime parser, canonical store, expression controller or original artwork in this task. Those files already had unrelated working-tree changes before this task.

## 2. Procedural eye integration

`Eyes` accepts `renderer="procedural"` and uses `canonicalProductionGeometry` to select the existing `EYE_EXPRESSION_PRESETS`. It renders the existing `ProceduralEye` in independent left/right positioned wrappers. All seven expressions are explicit; no unknown expression is substituted with Idle. Happy/ Shock share Idle artwork only through the existing verified preset mapping. Thinking-right retains its independent highlights; Thinking-left retains its distinct layered silhouette.

The existing geometry modules and `ProceduralEye.tsx` remain byte-for-byte unchanged. Gradients, outlines, masks, filters, transforms, water, highlights and SVG references are generated by the validated original engine. Canonical instances retain React `useId` resource scoping.

## 4. Face composition

The 1490 × 960 display aspect and centered 800 × 480 logical artwork are unchanged. Each wrapper converts logical coordinates to percentages once; inline SVG fills that wrapper. No second scale transform is introduced.

The established stacking order remains:

| Layer | z-index |
| --- | ---: |
| Face base | 0 |
| Face lines, clipped to the artwork window | 10 |
| Reserved existing under-eye effects | 15 |
| Eyes | 20 |

The expression composition itself occupies the existing stacking context above the base/lines. All currently mapped expression effects use the effects level. Morph effects live in full-size positioned groups at that level and crossfade existing artwork; no new effects were designed. Cry strips retain their intentional overflow into the display margin. Thinking asymmetry and all canonical expression-specific positions remain in `FACE_LAYER_LAYOUTS`, which is unchanged.

## 5. Expression controller integration

Live rendering reads the original store through `FaceRenderer`; selecting the procedural renderer changes only visual ownership. It creates no second canonical store and sends no semantic command. Manual/WebSocket validation, names, intensity metadata and duplicate semantics remain unchanged. Visual intensity remains unimplemented, as before.

Optional `expression`/`duration` props support isolated comparison instances. These override only that renderer's visual input. The separate development comparison uses local React state and never invokes `requestExpression` or `setState` on the store. Live manual controls retain their intended controller behavior.

## 6. Supported transitions

The existing coordinator/strategy selector gains a procedural `GEOMETRY` branch. These existing direct eye correspondences are reused in both directions:

- Idle ↔ Happier
- Idle ↔ Sad
- Idle ↔ Cry
- Sad ↔ Cry
- Idle ↔ Thinking

`sampleProductionGeometry` calls the original `interpolateEyeGeometry` dispatcher and layout interpolator. Mouth frames reuse `sampleIdleMouthTransition`, including Happier → Happy mouth mapping. Sad/Cry mouth artwork and placement already match, so that mouth remains unchanged through their transition.

Following browser feedback, route selection now treats the two channels independently. Happy/Shock eye artwork and layouts explicitly share Idle, so Idle ↔ Happy/Shock retains those exact eyes while the mouth morphs. Happier ↔ Happy changes only the eyes. Non-Idle eye pairs without a direct correspondence use source → Idle → target; distinct non-Idle mouth presets do the same, except identical Happy/Happier or Sad/Cry mouths remain unchanged. Each two-leg channel uses half of the requested total duration per leg. A direct or unchanged channel can run alongside a two-leg channel; the semantic store never changes to Idle. No new direct contour correspondence or arbitrary path interpolation was added.

`GeometryTransitionLayer` mounts untouched canonical source/target scenes and a separate intermediate scene. The coordinator animates one `data-progress` attribute through the existing engine, with the requested duration and linear timing used by composition transitions. Frame callbacks patch generated SVG attributes and placement directly, with no per-frame React publications or Zustand writes. Pure source presets are reused; the initial intermediate scene is memoized. The DOM patch retains matching nodes/defs across frames and uses a unique scope per mounted transition/side. Mouth clipping and tongue-only opacity retain the existing interpolation behavior.

At progress 0/1 the original canonical React scenes are displayed, not reconstructed DOM endpoints. At an internal Idle bridge, the adapter can restore the exact React-rendered Idle eye structure from a hidden template, with unique remapped resource IDs. It replaces structure only when topology changes, and retains resource nodes within a topology branch. Mouth clipping is added/removed as required when passing through an unclipped Idle frame. Decode readiness, no-driver immediate settlement, zero duration, reduced motion, cleanup and guarded stale callbacks remain under the existing coordinator/hook/engine.

## 7. Routed transitions and asset fallback policy

All 42 distinct canonical pairs now select `GEOMETRY` in procedural mode. Pairs without direct correspondence use the existing validated Idle legs as described above. No canonical procedural pair crossfades the entire face. Expression effects still fade independently, as before. The asset renderer retains its existing transitions, including its Idle → Happy element preset and other full-composition crossfades. Unknown expressions remain rejected and are not mapped to Idle; the Idle bridge is an explicit animation route, not a semantic expression fallback.

On interruption of a geometry transition, the previous target is settled to its exact canonical endpoint, then the latest request selects a fresh morph route. This can visibly snap during a rapid replacement. It avoids treating unapproved intermediate geometry as a canonical morph source. At most two composition records are retained. Asset crossfade interruption retains the existing more-visible-endpoint rule. Semantic duplicates do not restart animations.

The static `happier-transition` preview always uses its original assets and immediate preview behavior, even when procedural mode is selected. It remains outside protocol emotions.

## 8. Blinking compatibility assessment

Production blinking is **disabled** in both modes; no automatic blinking was added. Existing blink previews are retained.

`generateExpressionBlinkGeometry(expression, side, progress, source)` validates that `source` is data-equal to the named canonical preset. Morph frames alter contours, dimensions, resources or highlights and fail that contract. The production verification asserts rejection for every tested morph sample rather than bypassing the guard. Canonical open endpoints still return the original geometry object.

A later blink integration needs explicit support for the current morphed silhouette: upper/lower lid landmarks, aperture/boundary correspondence, masks, highlights, Sad attachments, Cry water/blur, endpoint equivalence, cancellation and resumption. Both sides and every supported morph direction require validation. Current canonical blink success does not prove that combined pipeline.

## 9. Renderer fallback and migration

`FaceRenderer` defaults to `renderer="asset"`. In Vite development, the live **Live renderer** selector opts the existing face into procedural mode. Switching modes remounts visual animation ownership, cancels the old engine lifecycle, and preserves the full canonical state and request metadata.

The separate **Production renderer comparison** panel provides local expression selection, asset/procedural/reference views, side-by-side inspection, current expression, renderer status and immediate/300/1000 ms transition testing. It now labels each eye/mouth route as direct, via Idle, or unchanged, and explicitly distinguishes original asset fades from procedural morphs. All seven canonical expressions are available. Its UI is removed from the production bundle, while production geometry adapters remain available via the renderer prop. Existing eye/mouth/blink previews remain available.

Migration procedure:

1. Keep the default asset mode; use the development selector/panel to compare every endpoint and supported direction.
2. Review Chrome/Brave scheduling, rapid requests, mode switches, reduced motion, responsive sizing and the target display. Resolve/accept the recorded differences below.
3. Only after those gates pass, explicitly select procedural mode at the production caller in a separate change. This task does not make that change.
4. Roll back by selecting/passing `asset`. No artwork restoration, schema change or data migration is needed.

- All 12 Sad/Cry/Shock/Thinking mouth comparisons have zero differing RGBA pixels.
- Idle mouth differs by one pixel at 1× and 2×; Happy/Happier mouths differ by one pixel at 2×. Maximum channel difference is 16; their other tested scales are exact. These preserve the pre-existing Idle/Happy outline rounding tolerance; geometry was not rewritten to conceal the difference.

| happier | 80 | 43 |

Standalone exact endpoint checks do not eliminate composition-level raster differences between embedded asset images and inline SVG at fractional display scale. Their precise rendering cause has not been isolated; no whole-face parity claim is made. No visible face redesign or new layer displacement was observed in these sheets.

Original PNG masters also differ from the asset composition before this integration. The largest visible discrepancy remains Cry: its original master has soft tear gradients and different termination, whereas the unchanged SVG effect strips have flatter color and extend below the face. Reference-versus-asset differing-pixel counts range from 44,162 to 145,326 in this static export methodology; these are image differences, not performance measurements.

## 13. Known limitations

Browser/Brave and hardware verification remain outstanding. Whole-face raster parity is not established. Existing tiny mouth endpoint differences and master-versus-SVG differences remain visible/measured. Production blink is disabled. Some channels visibly pass through Idle over two legs; this is a deliberate route using existing geometry, not a newly designed direct morph. Rapid morph interruption may snap to a canonical target. Morph frames may change between ellipse-based and layered implementations near endpoints and internal Idle bridges; existing approximation bounds and endpoint tests remain in force.

The comparison panel reports the selected branch, not a measured animation-completion timestamp. Intensity, visemes, speaking, audio sync, gaze and squash/stretch remain outside this task. Effects retain the original assets. No backend integration was expanded.

## 14. Production readiness assessment

The seven-expression procedural path is integrated with the actual production expression/rendering architecture and passes the listed functional/static raster gates. It is suitable for opt-in development comparison. It is **not approved as the production default** until browser and target-display review, continuous-motion review and composition-level differences are resolved or explicitly accepted. The original asset renderer remains a usable fallback.

## 15. Recommended next phase

Complete Chrome/Brave and target-display validation first: all canonical endpoints, all supported/reverse transitions, rapid replacement, reduced motion, renderer switches, resize and transparent margins. Record actual device/software/methodology for any performance measurements. Then define and validate a morph-aware blink geometry adapter before considering production blinking. Visemes/audio/backend work should remain a separate phase.
